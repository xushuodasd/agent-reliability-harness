# 持久化累计预算账本 v1（独立离线组件）

## 本轮实施契约

- 新建 SQLite 文件，绑定不可变的计划 SHA-256、token 上限与金额上限；打开已有账本必须
  提供相同计划摘要。不存在的账本不得在恢复时自动创建，已有文件不得覆盖。
- 金额使用整数 nano-USD（1 USD = 1,000,000,000 单位），token 为整数；拒绝 bool、
  浮点、负数及超出 SQLite 有符号 64 位范围的单项。上限为正数，请求估计/实测可为零。
- `reserve` 在事务提交后才返回首次放行 True；相同请求 ID、相同声明重放返回 False，
  **False 不授权再次发请求**，不同声明必须拒绝。请求 ID 不能跨 episode 或用途复用。
- 预留同时占用 token/金额余额；`settle` 记录实际量并释放剩余预留。结算超过预留也必须
  如实保存，永久标记 overrun，停止后续新预留，不能丢弃不利计量。
- `mark_unknown` 表示用量无法核实，保留完整预留，并停止所有新预留；重复标记无新事件。
  不自动释放、不自动重试、不将未知记零；v1 不提供人工对账或解除未知的入口。
- 进程重开后 pending 仍占用预算，既不清零也不重新放行。并发连接用 SQLite 写事务
  序列化检查与预留，避免两个请求同时消费同一剩余额度。已经在途的请求仍可结算。
- 只保存不含凭据的请求/episode 标识、用途(action/preflight/fallback)、整数计量与状态；
  配置和状态事件仅追加。每次读写都回放验证事件，不信任缓存计数。哈希不是签名。

## 边界和后续

新增的[单次传输桥接](budgeted-transport.md)供调用方显式使用；旧 CLI 尚未默认接入，
完整运行器、冻结请求绑定和恢复对账仍待完成。以下是账本自身的边界。

这是预算状态机，不是已经接入 HTTP 的完整消费保护。调用方尚须在**每一次**实际发送前
调用 reserve（包括 preflight 和兼容回退），保证预留覆盖保守上界，发送后结算；不确定
结果必须 mark_unknown。进程可能在预留后、发送前或发送后崩溃，v1 只能保留占用，不能
证明服务是否执行，也不承诺 exactly-once 网络调用或绝对金额上限。

真实费用依赖安全凭据、准确费率、计费项目、token 上界与供应商对账。本轮不接真实 API，
不读取凭据，不改写旧运行证据。新建另一个账本不能被当成用户授权追加预算。正式实验
仍需固定协议，并完成传输层接入、24-episode 开发上限和恢复路径验证。

## 接口与恢复规则

`BudgetLedger.create(path, plan_sha256, max_tokens=..., max_nanousd=...)` 只创建新账本；
`BudgetLedger(path, plan_sha256)` 打开旧账本。`snapshot()` 返回已结算已知量、未结算
预留量、可用余额、阻断状态和请求列表；不是完整供应商账单。

`reserve(request_id, episode_id, operation, tokens=..., nanousd=...)` 的估计必须由调用方
保守给出；`settle(request_id, tokens=..., nanousd=...)` 的实测需先经过响应校验。
v1 的 unknown 不可重新结算或释放；需要对账时必须保留原账本并另行设计有证据的流程。
后端不会替调用者发请求，也不会依据结果筛选保留哪些 episode。

SQLite 事务保护同一个本地文件的并发访问，不用于网络共享盘的分布式预算保证。
恢复不自动创建文件：若账本丢失（包括误删后从 Git 重新拉取），不得假定历史消费为零。
运行数据库和凭据都不应提交到 Git；应采用私有备份及独立对账记录。SQL 追加约束和回放
校验防普通误改，不防持有文件写权限的人替换整个账本或删除触发器。
